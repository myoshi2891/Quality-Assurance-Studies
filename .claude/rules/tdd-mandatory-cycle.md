# TDD 必須サイクル & コミット分割ルール

プロジェクトの品質とトレーサビリティを担保するため、以下の TDD サイクルおよびコミット分割を**絶対的な強制ルール**として適用する。

## 核心原則

<ai_agent_directive>
**AI エージェントへの厳格な指示**: 
1. **Red（テスト失敗）フェーズを経ないコード実装は「未完了」とみなす。** 実装コードを書く前に、必ず失敗するテストをコミットすること。
2. **一括コミットの禁止。** 「テスト + 実装 + ドキュメント」を一つのコミットにまとめることは重大な規約違反である。
3. **自律的な修復。** サイクルを飛ばしたことに気づいた場合、直ちに `git reset` 等で戻り、正しい手順（Red -> Green -> Refactor）をやり直すこと。
</ai_agent_directive>

## 必須ワークフロー

### ステップ 1: Red（テストの作成と失敗）
- 実装する機能の仕様を反映したテストファイルを `tests/` 下に作成。
- **実行**: `bun test` で失敗（またはコンパイルエラー）を確認。
- **コミット**: `test(<scope>): add failing spec for <feature>`

### ステップ 2: Green（最小実装と成功）
- テストをパスさせるための最小限のコードを `app/` または `components/` 等に実装。
- **実行**: `bun test` でパスを確認。
- **コミット**: `feat(<scope>): <feature implementation summary>`

### ステップ 3: Refactor（リファクタリング・最適化）
- コードの重複削除、読みやすさの向上、ビルド/リンターエラーの修正。
- **実行**: `bun run build` および `bun run lint` を実行。
- **コミット**: `refactor(<scope>): <clean up or optimization>`

### ステップ 4: Docs Sync（進捗同期）
- 移行プロジェクトの場合、`MIGRATION_PROGRESS.md` を更新。
- **コミット**: `chore(docs): update MIGRATION_PROGRESS.md — <page/feature name>`

## 除外事項
- 既存ファイルの誤字修正や、コードロジックに影響しないコメントの微修正のみ。
- ただし、少しでもロジックが変わる場合は、テストの更新または追加を検討すること。

## 違反時の対応
このルールを無視した場合、ユーザーからの指摘を待たずに自ら `git reset` を行い、正しい TDD サイクルを再実行しなければならない。
