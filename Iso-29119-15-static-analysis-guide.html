Step 2. 静的解析とは

静的解析 ＝ プログラムや成果物を「実行せずに」調べ、欠陥・リスク・規約違反を見つける活動です。Metaの Peter O'Hearn 氏もCACM論文で、静的解析ツールを「他のプログラムのソースを、実行せずに調べて結論を導くプログラム」と説明しています。

観点静的解析動的テスト
実行不要必要
対象コード・仕様・設計・モデル・データ動くソフトウェア
得意な欠陥規約違反、未初期化変数、NULL参照の可能性、要件の矛盾性能、環境依存、実際の出力の誤り
時期早い（成果物ができた時点）実行可能になってから
弱点誤検知が出るテストした範囲しか確認できない

一般知識 静的解析には「ツールによる解析」と「人によるレビュー」の2つの顔があります。概要に「review techniques」とあるため、29119-15は両方を視野に入れていると読めます。

Step 5. 静的解析の一般的なプロセス（学習用モデル）

一般知識 以下は CD本文の内容ではありません。実務で回すときの一般的な流れを整理した学習用モデルです。

ステップやること具体例
① 計画目的・対象・合格基準を決める新規コードは重大度High指摘ゼロでマージ
② 準備ルール・ツール・担当を決める言語別Linter設定、レビュー担当割当
③ 実施ツール実行／個人レビューCIで自動実行
④ 分析指摘の真偽・重大度を判断誤検知の除外、優先度付け
⑤ 是正修正して再確認修正→再解析
⑥ 報告結果と判断を記録件数・傾向・未解決事項
⑦ 改善ルールとプロセスを更新誤検知の多いルールを無効化

Step 6. ツール解析のしくみ

手法一言で見つけられる例
字句・構文解析書き方のルールを機械的にチェック命名規則違反、未使用import
型チェック値の種類の整合性を確認数値に文字列を渡している
制御フロー解析分岐・ループの通り道を追跡到達不能コード
データフロー解析値の生成〜使用を追跡未初期化変数、NULL参照
テイント解析外部入力が危険箇所に届くか追跡SQLインジェクションの可能性
抽象解釈・記号実行実行パスを数学的に近似して推論配列範囲外、メモリリーク

具体例：実行せずに欠陥を見つける

def find_user(users, name):
    for u in users:
        if u["name"] == name:
            return u
    # 見つからないと None が返る

users = [{"name": "Bob", "email": "bob@example.com"}]
user = find_user(users, "Alice")
print(user["email"])   # user が None だと実行時エラー

ツールはプログラムを動かさず、「Noneを返す経路があるのに確認せず参照している」と指摘できます。

用語意味影響
偽陽性（false positive）問題がないのに「問題あり」と報告信頼低下、指摘が無視される
偽陰性（false negative）本当の問題を報告しない欠陥が残って出荷される

Step 7. 国際的な開発者の知見（一般知識）

事例要点学び
Meta：Infer / Zoncolan
Peter O'Hearn（CACM 2019）		すべてのコード変更に対して実行し、コードレビュー内でボットとして指摘。10万件超の指摘が本番前に修正された。一括（バッチ）実行は修正率0%、コードレビュー中の差分実行は70%「いつ・どこで見せるか」が成果を決める
Google：Tricorder
Sadowskiほか（ICSE 2015）		解析ツールを載せる共通プラットフォームと指導原則を整備。専門家でない開発者もルールを書け、データで改善するエコシステム組織として回す仕組みが重要
Coverity
Bessey, Englerほか（CACM 2010）		研究技術を商用化して顧客コードに適用した経験談。ビルド方法や言語方言の違いなど想定外の壁が多数。誤検知が増えると開発者の信頼を失う検出力と誤検知抑制のバランス設計

推測 この3つの教訓は、29119-15が目指す「汎用プロセス・活動・タスク・文書化」の方向性と重なると考えられます。

Step 8. 実務への活かし方

#導入チェック項目目的
1目的と合格基準を文書化したか何をもって合格かを明確にする
2対象範囲（コード・設定・仕様・モデル）を決めたか見逃し領域の把握
3ルールを少数から段階導入したか指摘の洪水を避ける
4指摘の分類基準（重大度・真偽）を決めたか判断のぶれを減らす
5誤検知の抑制ルール（理由の記録必須）を決めたか無視文化を防ぐ
6結果を記録・追跡しているか傾向分析と監査対応
7定期的な見直しの仕組みがあるか継続的改善
よくある失敗対策
初日に数千件の指摘が出て誰も見なくなる新規・変更箇所のみから開始（Metaの教訓と整合）
ルールが多すぎて開発者が疲弊重要度の高いルールに絞る
指摘が放置される是正の責任者と期限を決める
ツールだけで安心する静的解析と動的テストを併用する
