Step 1: 全体像をつかむ

1-1. 29119シリーズの中での位置づけ

Part 2が「プロセスの骨組み」、Part 4が「その中で使う道具箱」という関係です。

1-2. 技法の3分類

分類 設計の主な情報源 別名
仕様ベース 要件、仕様書、モデル、ユーザーニーズ ブラックボックス
構造ベース ソースコードやモデルの構造 ホワイトボックス
経験ベース テスターの知識と経験 ―

仕様と構造の両方の知識を組み合わせる場合はグレーボックスと呼ばれます。3分類は互いに補完的で、組み合わせるほうが効果的とされます。

1-3. 2021年版の主な変更点

  • 「テスト条件」を廃止し「テストモデル」を使う形に変更。旧版で「テスト条件の意味と、そこからテストケースを導く方法が分かりにくい」というフィードバックがあったためです（詳細は附属書H）。

Step 2: 技法に共通する3つの作業 TD1〜TD3

29119-2のテスト設計・実装は4活動で構成され、技法ごとに固有のやり方が必要なTD1〜TD3を29119-4が定義します。TD4（テスト手順の作成）は技法によらず共通です。

用語 意味 たとえ：ラーメン屋の味チェック
テストモデル 注目したい性質を表した表現（要件文、同値クラス、状態遷移図、決定表、制御フローグラフなど） メニュー表
カバレッジアイテム モデルの中で「テストで踏める」要素 メニューの各行（醤油、味噌、塩）
テストケース 事前条件・入力・期待結果の組 「醤油を注文してスープが熱いか確認する」1回の確認

例（状態遷移）：完了基準が「全状態を踏む」なら、TD1で状態モデルを作り、TD2で各状態をカバレッジアイテムにし、TD3で全状態を通る操作列を作ります。「全遷移」が基準なら、遷移まで書いたモデルが必要です。つまりテストモデルは完了基準に応じて選びます。

5.2.1 同値分割 同値クラス 入出力の値の整理

3-1. 同値分割と3-3. 境界値分析（年齢で料金が変わる例）

同値クラス：無効（−1以下）／子供（0〜12）／大人（13〜64）／シニア（65〜120）／無効（121以上）。各クラスから1つ選べば同値クラスカバレッジ100%です。

技法 テスト値 個数
同値分割 −5、6、30、80、200 5
境界値分析（2値） −1/0、12/13、64/65、120/121 8 
import pytest

def fare_category(age: int) -> str:
    if age < 0 or age > 120: return "error"
    if age <= 12: return "child"
    if age <= 64: return "adult"
    return "senior"

@pytest.mark.parametrize("age,expected", [
    (-1, "error"), (0, "child"), (12, "child"), (13, "adult"),
    (64, "adult"), (65, "senior"), (120, "senior"), (121, "error"),
])
def test_boundaries(age, expected):
    assert fare_category(age) == expected

3値流儀（境界とその両隣）を使う場合は、どの流儀にするかを組織で決めておきます。

3-5. 組合せテスト（P-Vペア）

技法 内容 テスト数
全組合せ すべての組合せ 最大（爆発しやすい）
ペアワイズ 任意の2パラメータの値の組をすべて網羅 少ない
各選択 各値が少なくとも1回出る 最小クラス
基底選択 標準値を基準に1パラメータずつ変える パラメータ数に比例

OS(3)×ブラウザ(3)×言語(2)は全組合せ18通りですが、ペアワイズなら9通りで済みます。実務ではPICTなどのツールを使い、「存在しない組合せ」の制約の扱いが鍵になります。

3-6. デシジョンテーブル（送料ルール）

条件・動作 R1 R2 R3 R4
会員である Y Y N N
購入額5,000円以上 Y N Y N
送料無料 ○ × ○ ×
ポイント2倍 ○ × × ×

4規則＝4テストケースで決定規則カバレッジ100%です。条件が増えて列が爆発したら、結果が変わらない条件を「−（無関係）」にまとめて縮約します。原因結果グラフは、条件間の論理関係が複雑なときにグラフで整理してからこの表に落とす技法です。

3-8. 状態遷移テスト（注文ステータス）

カバレッジ基準 アイテム この例での数
すべての状態 状態 7
0-switch 実状態間の有効な単一遷移 6（[*]との矢印は数えない）

「下書き→出荷済み」のような無効な遷移が拒否されることの確認は、状態表を使うと漏れにくくなります。

3-4／3-7／3-9〜3-12. その他の技法

  • 構文テスト：入力形式をBNFで定義し、正しい例と「規則を1か所だけ破った例」を作る。書式の検証だけで、実在する日付かどうか（例：02-31）は別の技法で確認します。
  • シナリオテスト：他システム（ユーザー含む）との相互作用の流れを、主・代替・例外シナリオで確認。同値分割の入力値を各ステップに使う組合せも可能。
  • ランダムテスト：入力分布に従い無作為に入力を選ぶ。認識されたカバレッジアイテムはなく、期待結果の判定（オラクル）が課題。
  • メタモルフィックテスト：「入力をこう変えれば出力はこう変わる」という関係で既存テストから新テストを作る。例：検索語に絞り込みを足すと件数は増えない。AI・MLのテストで注目されます。
  • 要件ベーステスト：要件をこれ以上分割できない原子的要件に分解し、それぞれにテストを作る。

Step 4: 構造ベース技法（7種類）

共通の題材として次の関数を使います。

def grant_access(is_admin: bool, is_active: bool, has_token: bool) -> bool:
    if is_admin and (is_active or has_token):   # 判定（decision）
        return True
    return False
用語 意味 例
条件 論理演算子を含まない真偽式 is_admin、is_active、has_token
判定 条件を論理演算子でつないだ式 is_admin and (is_active or has_token)

7技法は、文テスト／分岐テスト／判定テスト／分岐条件テスト／分岐条件組合せテスト／MCDCテスト／データフローテストです。

文カバレッジの限界y=0; if x>0: y=1; return y を f(1) だけで試すと文カバレッジは100%ですが、if が偽になる経路は未実施で分岐カバレッジは50%です。

テスト数の比較（上の例）

技法 テスト数 ひとこと
判定テスト 2 真と偽の両方を出す
分岐条件テスト 4 Pythonの短絡評価で評価されなかった条件は数えない
MCDCテスト 4（n+1） 各条件が単独で判定結果を変えることを示す
分岐条件組合せテスト 8（2n） 条件が増えると指数的に増える

MCDCの具体例

TC is_admin (A) is_active (B) has_token (C) 結果
M-1 True True False True
M-2 False True False False
M-3 True False False False
M-4 True False True True

独立影響のペア：A＝M-1とM-2、B＝M-1とM-3、C＝M-3とM-4。MCDCは航空ソフトのDO-178Bレベル最上位で要求されることで知られ、NASAのチュートリアル（Hayhurstほか、2001）が定番の解説です。一部のカバレッジツールは厳密な解釈を使わず、実際には満たしていないのに100%と表示する場合があるため、認証目的ではツールの適格性評価が必要です。

データフローテストは、変数の定義（def）と使用（c-use／p-use）のペアを網羅し、「定義した値が使われない」「定義前に使う」といった変数まわりの不具合に強い技法です。

Step 5: 経験ベース技法（1種類）

エラー推測：テスターの経験や過去の欠陥データから「壊れやすい箇所」を推測してテストを作ります。手順は、欠陥リストを作る→各項目に対応するテストを設計→実行して記録、の3段階です。

種類 例
空・欠損 空文字、null、未入力
極端な長さ 1文字、上限+1文字、10万文字
特殊文字 引用符、改行、絵文字、サロゲートペア
日時 うるう日、月末、タイムゾーン境界、サマータイム切替
同時実行 ダブルクリック、二重送信、同時更新

探索的テストそのものは29119-1の扱いで、探索的テストの中でエラー推測などを使う、という関係です。

Step 6: テストカバレッジ測定（第6章）

カバレッジ（%）＝ 踏んだカバレッジアイテム数 ÷ 全カバレッジアイテム数 × 100（例：5クラス中4クラス実行＝80%）

適用上の注意構文テスト・ランダムテスト・メタモルフィックテスト・エラー推測には、業界で合意された計算方法がありません。このうちランダムテストとエラー推測には、認識されたカバレッジアイテム自体がありません。これら4技法には上の式をそのまま当てはめないでください。

Martin Fowler は、カバレッジの数値は「テストされていない部分を見つける道具」としては有用だが、テストの良さを表す数値としてはほとんど役に立たない、と述べています。

良い使い方 悪い使い方
未テスト箇所を探す カバレッジ%を品質の証明にする
技法の選択とセットで目標を決める 全社一律のカバレッジ目標を置く
重要な判定にだけ強い基準（MCDC等）を使う 全コードに最強の基準を求める

Step 7: 技法の選び方

規格は文脈ごとの選択指針を与えません。以下は初学者向けの実務的な目安（規格の規定ではありません）です。

状況 候補となる技法
フォームの入力チェック 同値分割、境界値分析、エラー推測
料金計算・権限判定 デシジョンテーブル、境界値分析、MCDC（重要な場合）
ワークフロー・ステータス管理 状態遷移、シナリオ
設定項目が多い製品の互換性 ペアワイズなどの組合せ

機械学習・科学計算 メタモルフィック、ランダム
安全重視の組込みソフト MCDC、データフロー

Step 8: 適合性（Conformance）の考え方

種類 内容
完全適合 選んだ技法（空でない集合）について、第5章の技法と第6章の測定方法のすべてのshallを満たす
調整適合 一部だけでもよいが、調整の理由を記録し、リスクを考慮し、関係者の合意を得る
  • 全技法を使う必要はない（例：境界値分析だけで適合を主張してもよい）。
  • 組織は完全適合か調整適合かを明示しなければならない。

Step 10: 実務での注意点と批判的視点

  • 29119-4は技法の辞書であり、「必ずこの方法で」と命じるものではありません。技法集は網羅的でないと明記されています。
  • 2014年ごろ、James Bach、Cem Kaner、Association for Software Testing などから29119の撤回を求める声がありました（専門家間の合意不足、文書化偏重、コンテキスト駆動テストの排除、規定が細かすぎる、など）。Stuart Reid らは反論を公表しています。この批判は主にシリーズ全体（プロセスや文書化）に向けたもので、Part 4の技法そのものへのものではありません。Wikipedia経由の要約で、各原文は未読です。
  • 初学者への助言：規格を「守るべき規則」ではなく「共通語彙とチェックリスト」として使う。
落とし穴 対策
技法名の暗記で満足する 小さな仕様で実際にテストケースを導出する
カバレッジ100%を品質の証明とみなす 抜けの発見に使う。期待結果の正しさは別問題
境界値を−1/+1で機械的に決める 浮動小数点や日時は境界の定義と最小単位を先に決める
無効な遷移を試さない 状態表で「許されない遷移」も明示的にテストする
MCDCをツール任せにする 適格性評価済みのツールを使う
組合せ爆発を放置する 制約付きペアワイズで絞り、リスクに応じて強度を上げる

演習問題

問題1　パスワード長が8〜64文字で有効。同値クラスと2値境界値のテスト値は？

無効（7以下）／有効（8〜64）／無効（65以上）の3クラス。境界値は 7、8、64、65 の4個。

問題2　A and B のMCDCに必要な最小テスト数と1例は？

n+1＝3ケース。(A,B)＝(T,T)→真、(F,T)→偽、(T,F)→偽。Aは1番目と2番目、Bは1番目と3番目のペアで独立影響を示せる。

問題3　正解の並びを決めにくい検索結果の並び替え機能に使える技法は？

メタモルフィックテスト（例：キーが一意なら入力順を入れ替えても結果は同じ。キーが重複すると同順位の並びが入力順に左右され得る）とランダムテストの組合せ。性質を使ったオラクルで判定する。

問題4　テストモデル・カバレッジアイテム・テストケースの関係は？

テストモデルは対象の注目点を表した表現。その中の「踏める要素」がカバレッジアイテム。それを踏むように事前条件・入力・期待結果をまとめたものがテストケース。
