1. 一言でいうと

✅ この文書は、ユースケースを作る「プロジェクト」をどう進めるか のベストプラクティスをまとめたものです。扱う観点は次の3つです（Scope より）。

  • プロジェクト（Use case projects）: どんな目的のユースケースプロジェクトがあるか
  • テンプレート（Use case templates）: ユースケースを書く書式をどう設計するか
  • 計画（Use case project plans）: 組織運営・テンプレート・ユースケースをどう作って保守するか

ポイントは、システムの作り方ではなく、ユースケースを集めて整える活動の進め方 を対象にしていることです。

4. 前提知識: ユースケースとは

4.1 規格の序文が述べていること（✅）

序文は、ユースケースの概念が 1980年代にシステム工学で Ivar Jacobson によって導入された と述べています。目的は、システムの要求を、テキスト・構造・視覚的なモデリング技法で捉えて仕様化することです。また、研究の場で広く使われ、標準化の場でもほぼ体系的に使われている として、次の例を挙げています。

領域 序文が挙げる例
方法論 IEC 62559
生活支援 AAL（Ambient Assisted Living）のユースケース
ビッグデータ ビッグデータ領域のユースケース（NIST による3回の反復を含む）
IoT IoT 領域のユースケース
AI AI 領域のユースケース（セキュリティ・プライバシーの付随規格を含む）
デジタルツイン デジタルツイン領域のユースケース
ブロックチェーン ブロックチェーン領域のユースケース
プライバシー 消費者分野のプライバシー・バイ・デザインのユースケース

また、第1〜9図は UML 図の記法で描かれていると書かれています。

4.2 用語定義（✅ 第3章の冒頭、意味を日本語で言い換え）

用語 意味
actor（アクター） ユースケースに関わる利害関係者
role（ロール） 対象システムと相互作用する外部のアクターや当事者が担う機能・役割。当事者には機能、システム、組織、デバイスが含まれる
stakeholder（ステークホルダー） ユースケースに直接または間接に影響を受ける、または影響を与える個人・チーム・組織（またはその種類）
use case（ユースケース） システムが行う一連の動作の仕様で、1つ以上のロールや他のステークホルダーにとって、通常は価値のある観察可能な結果を生むもの（ISO/IEC 19505-2:2012 に基づく）

4.3 補足: テキスト中心の考え方（💡）

ユースケース技法の代表的な解説書に、Alistair Cockburn の Writing Effective Use Cases（2001）があります。出版社の紹介では、アクター、ステークホルダー、設計スコープ、ゴールレベル、シナリオといった要素を扱うとされ、書評では、ユースケースを図ではなくテキスト中心の成果物として捉える立場が紹介されています。30194 の序文が「テキスト、構造、視覚的なモデリング技法」と書いていることとも整合します。

7.1 読み取れること（💡）

  • テンプレートは 記述ブロック → 定義済みフィールド・記述指示・記入例 で成り立つ、という設計になっていると読めます

項目 内容
名称 灌水量の最適化提案
目的 水と肥料の使用量を抑えつつ収量を維持する
アクター 農家、土壌センサー、気象API、デジタルツイン、予測サービス
ロール 農家＝提案の承認者、センサー＝データ提供者

ID 異常系の条件 期待される動作
E1 センサー欠測 近隣センサーで補完し、補完済みと明示して通知する
E2 気象API応答なし 過去平均で暫定提案し、再取得を試みる
E3 農家が24時間応答しない 提案を失効させ、再通知する
